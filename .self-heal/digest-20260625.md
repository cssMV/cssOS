## ② 真实 bug + 建议 diff

### 🟢 BUG-1 — person-mv 评论端点对非-person-mv 作品恒 404(88 次,今日活跃)

**根因。** 影院弹幕 `fetchDanmu(id)`([app.watch-cinema-caption.js:102](public/app.watch-cinema-caption.js:102))对**每一首**正在看的作品都打
`GET /api/person-mv/mvs/:id/comments`。但普通作品 / 市场作品的 id **不是** person-mv 的 mv_id,后端
[src/index.ts:48674](src/index.ts:48674) `resolvePersonMvId(raw)` 返回 null → `return res.status(404)`。
遥测里 id 被 `[0-9a-f-]{8,}→#` 掩码,所以显示成 `/api/person-mv/mvs/#/comments`。

**用户影响 = 无**(前端 `r.ok ? json : null` 已吞掉 404,只是没有弹幕)。**唯一代价 = 404 遥测噪音**
(fetch 探针上报 ≥400 且非 401/403/402)。属"假阳性污染 digest",不是功能损坏。

**建议修复(主推:后端 404→200 空列表)。** 一个只读公开评论列表,"未知 id → 空列表"比"404 NOT_FOUND"更符合 REST,且彻底消噪。风险 **低**(POST 评论端点仍各自校验 mv_id;GET 仅是公开读)。

```diff
--- src/index.ts  (@48668 GET /api/person-mv/mvs/:mv_id/comments)
     const mvId = await resolvePersonMvId(raw);
-    if (!mvId) return res.status(404).json({ ok: false, code: "NOT_FOUND" });
+    // CSSOS_SELFHEAL_20260625 — 影院弹幕对每首作品都查 person-mv 评论;
+    // 非 person-mv 作品的 id 解析为 null,旧逻辑回 404 → 海量无害 404 遥测噪音。
+    // 只读公开列表:未知 id 直接回空列表(语义 = "此 id 暂无评论"),消噪且不改前端行为。
+    if (!mvId) return res.json({ ok: true, data: [], comments: [] });
```

**备选(更保守:前端只对 person-mv 作品取弹幕)。** 在 `fetchDanmu` 加一道"是否 person-mv"判定再 fetch。
但 watch 作品来源混杂(plaza vs 普通影院),可靠判定较脆,故主推后端方案。

> 我**未**改动 `src/index.ts`(保持工作树干净)。上述 diff 已人工核对上下文一致,待 Jing 审核后再改+`deploy-express` 出 dist。
